# Бэкенд «Каспийского диспетчера»

FastAPI, один процесс. Контракт — раздел 5 `CLAUDE.md`. Эндпоинты считает **настоящий движок сценария**: состояние в памяти из `data/seed.json`, граф networkx, расписание рейсов, предиктор срыва стыковки (CatBoost или формула), диспетчер с принятием под блокировкой. Формы ответов те же, что были на моках.

## Запуск одной командой

Нужен Python 3.11+.

```powershell
.\run.ps1          # Windows
```
```bash
./run.sh           # macOS / Linux / Git Bash
```

Скрипт сам создаст `.venv`, поставит зависимости, скопирует `.env.example` → `.env` и поднимет сервер на `0.0.0.0:8000` с автоперезагрузкой.

Проверка: `curl -H "X-API-Key: <ключ>" http://localhost:8000/api/stats`. Ключ — `API_KEY` из `backend/.env`; для локального запуска `.env.example` ставит `caspian-dev-key`. На общем сервере ключ другой — его раздают в чате.

Тесты: `.venv/Scripts/python -m pip install -r requirements-dev.txt`, затем `.venv/Scripts/python -m pytest` (из `backend/`).

## Для фронтенда и Flutter

- **Базовый адрес:** `http://<ip-ноутбука>:8000/api` (локально `http://localhost:8000/api`). Телефон должен быть в той же сети; IP — `ipconfig` / `ifconfig`. Эмулятор Android ходит на `http://10.0.2.2:8000/api`.
- **Ключ:** заголовок `X-API-Key: <API_KEY из backend/.env>` на **каждом** запросе к `/api/*`. Локально из `.env.example` — `caspian-dev-key`, на общем сервере — ключ из чата. Без ключа — `401 {"error": {"code": "unauthorized", ...}}`.
- **WebSocket:** `ws://<host>:8000/ws?api_key=<ключ>` (браузер не умеет слать заголовки в WS). Сообщения `{type, payload}`: `shipment.updated`, `alert.created`, `alert.updated`, `ledger.appended`, `stats.updated`, `weather.updated`. Не успеваете с WS — опрашивайте `/shipments`, `/alerts`, `/stats` раз в 3 с.
- **Документация и «попробовать»:** http://localhost:8000/docs (Swagger, кнопка **Authorize** → ключ), схема — `/openapi.json`.
- **Время** в JSON — UTC (`2026-11-12T11:00:00Z`). Показывать в `Europe/Moscow`.
- **Ошибки** всегда `{"error": {"code": "...", "message": "..."}}`.

### Два времени

- **«Сейчас» сценария** (`sim_now`) — по нему считаются прогноз, рейсы, задержки, положение грузов. При каждом reset (и при старте) это текущее время, отброшенное до часа (10:52 → 10:00). Сценарий привязан к нему, а не к календарю: `seed.json` хранит времена от якоря `meta.now` (12 ноя 14:00 МСК), и при reset всё сдвигается на `sim_now − якорь`. Поэтому шторм всегда через 36 ч, паром А — через 44 ч, паром М — через 64 ч, и все числа сценария прежние. До следующего reset `sim_now` не идёт, числа не плывут.
- **Метки событий** (`accepted_at`, `ts` блока, время выдачи пропуска) — настоящее время: в боте «Принято в 10:52».
- `DEMO_NOW` в `.env` (UTC) фиксирует `sim_now` руками; тогда метки событий = `DEMO_NOW` + прошедшее с reset. Тесты и моки всегда идут по 12 ноя 14:00 МСК.

Повторный прогон после reset даёт те же числа и маршруты; даты, хэши блоков и токены пропусков меняются вместе со временем.

### Погода

`WEATHER_MODE` в `.env`:
- `live` (по умолчанию) — волна из Open-Meteo Marine, ветер из Open-Meteo Forecast, точки портов Каспия (Астрахань и Оля — ближайшее открытое море: сами порты на суше), `forecast_days=7`, обновление раз в 30 мин, кэш в `data/weather_cache.json`. Источник недоступен — работаем по кэшу: `source: "cache"`, `stale: true`, если кэшу больше часа. Нет ни сети, ни кэша — синтетический прогноз, `stale: true`.
- `synthetic` — всегда синтетический прогноз, сеть не трогаем, `source: "cache"`. Страховка на защиту: на Каспии правда шторм или нет интернета.

Сценарий накладывается поверх прогноза: в окне шторма волна поднимается до значений сценария, вне окна остаётся реальной. До сценария риски грузов (на синтетике у формулы 7/4/3%) зависят от настоящей волны и могут немного отличаться.

### Предиктивная модель

`PREDICTOR` в `.env`: `catboost` (по умолчанию) или `formula`. Если файла `data/model.cbm` нет или catboost не импортируется, сервер стартует на формуле и пишет причину в лог. Она же видна в `GET /api/model` → `fallback_reason`.

Что считает модель, а что код:
- **вероятность срыва стыковки** (`Risk.miss_probability`) — классификатор CatBoost (`data/model.cbm`);
- **сдвиг отправления, задержки, деньги, CO₂ и `Risk.factors` в часах** (волна 11 ч, очередь 5 ч, таможня 2 ч) — расчёт по прогнозу погоды и расписанию рейсов. От модели не зависят: +18 ч, +48 ч, +6 ч, 126 груз-ч, 596 640 ₽ одинаковы у обоих предикторов;
- **`Risk.probability_drivers`** (необязательное поле, только у CatBoost) — три главных признака по SHAP классификатора: `{name, label, impact_pp}`. `impact_pp` — вклад в вероятность в процентных пунктах: насколько вероятность была бы ниже без вклада этого признака. К сумме ничего не подгоняется. У формулы и сухопутных маршрутов поле `null`;
- **регрессор сдвига** (`data/model_shift.cbm`) — только проверка: MAE в отчёте и график «прогноз против факта». На сервере не используется.

Вероятности на шторме у модели не обязаны быть ровно 82/74/68%. Допуск ±5 п. п. и порядок №01 > №02 > №03 проверяют тесты и `/api/demo/check`. Тексты бота и сайта берут проценты из ответа модели.

**Обучена на синтетической истории.** `scripts/gen_history.py` генерирует 30 000 стыковок по правилам из `docs/PLAN.md` (seed 42): волна до 2 м не влияет, на 2–3,5 м задержка растёт, выше паром стоит; загрузка порта нелинейна после 0,8; лёд в Астрахани и Оле с декабря по март; логнормальная таможня; шум и выбросы. Прогноз шторма сбывается не всегда. Метрики показывают работу конвейера, а не точность на реальных данных. На истории порта модель переобучается без изменения кода.

```bash
.venv/Scripts/python -m pip install -r requirements-dev.txt
.venv/Scripts/python scripts/train.py --regen   # история → модели → data/model_report.json → графики
```

`train.py` откладывает 20% выборки и пишет в `data/model_report.json` AUC, Brier, MAE, размеры выборок, дату, seed, параметры шума и важность признаков. Графики — в `docs/pitch/model_calibration.png` и `docs/pitch/model_pred_vs_fact.png`. В конце скрипт прогоняет `storm_north` через движок и падает, если вероятности вне допуска. Тогда правится генератор, а не ответы модели. Модели, история и отчёт лежат в git, на ноутбуке для демо обучать не нужно.

`GET /api/model` — только чтение: `summary` — заметная строка «Активен предиктор: CatBoost (…)» или «…логистическая формула — ОТКАТ с CatBoost: <причина>»; та же строка пишется в лог при старте (при откате — warning). Дальше `active`, `fallback_reason`, `synthetic: true`, `note`, `used_at_runtime` (вероятность — классификатор CatBoost; сдвиг и задержки — расчёт по прогнозу погоды и расписанию; регрессор — только проверка), метрики классификатора и регрессора, важность признаков.

### Проверка перед показом

`GET /api/demo/check` (только демо) сначала проверяет **начальное состояние**: до сценария ни один груз не «Под риском» на текущей погоде и активном предикторе (`calm_start`; при провале в `problems` — например «№01 под риском до сценария: риск 64%, волна в порту Астрахань 2,3 м (предел 2,5 м), ветер 14 м/с, загрузка 62%, запас 2 ч»). Затем прогоняет `storm_north` на копии исходного состояния (как после reset, с текущей погодой) и ничего не меняет. Ответ: `ok`, список сверок с эталоном (риски 82/74/68% ±5 п. п. и порядок №01 > №02 > №03; точно: +18 ч, +48 ч, +6 ч, 126 груз-ч, 596 640 ₽, рекомендован вариант через Махачкалу) и `problems` — почему разошлось, например «волна в Махачкале 2,8 м в момент отправления парома М (15 ноя, 06:00), предел 2,5 м — вариант через Махачкалу отпал». Если разошлось — `WEATHER_MODE=synthetic` и перезапуск. Та же проверка пишется в лог при старте и при каждом reset.

### Сценарий демо

| Шаг | Запрос | Что поменяется |
|---|---|---|
| Проверка | `GET /api/demo/check` | ничего; `ok: true` — числа сценария сойдутся |
| Исходное состояние | `POST /api/demo/reset` | №01–03 «В пути», риск низкий (формула 7/4/3%, у модели свои значения), алертов нет, счётчики 0 |
| Съёмка инвойса №05 | `POST /api/documents` (multipart `shipment_id=sh-05`, `file`) → `POST /api/documents/doc-05/confirm` `{"fields": {...}}` | черновик с полями (фарси → русский; сейчас закэшированный результат), затем пропуск `pass-05` и блок `issued` |
| Шторм | `POST /api/scenarios` `{"preset": "storm_north"}` | №01–03 «Под риском» 82/74/68% (у модели ±5 п. п.), отправление +18 ч, морской этап `blocked`, ETA +48 ч, алерт `alert-001` (`new`) |
| Сбой пропуска (по желанию) | `POST /api/demo/fail_next_pass` перед «Принять» | у первого груза `pass_state: reissue_pending`, старый пропуск активен |
| Принятие | `POST /api/alerts/alert-001/accept` `{"via": "web"}` (или `"telegram"`; `option_id` — другой вариант) | через Махачкалу, «Перестроен», новые пропуска `pass-0N-r1`, старые `reissued`, блоки `reissued`, место на пароме М зарезервировано, счётчики 126 груз-ч / 596 640 ₽ / 1 824 кг CO₂. Повтор → `already_accepted: true` |
| Повтор пропуска | `POST /api/shipments/sh-01/pass/retry` | пропуск выпущен один раз, экономия не меняется |
| Отклонение | `POST /api/alerts/alert-001/reject` | алерт `rejected` |
| Подделка реестра | `POST /api/ledger/tamper` `{"index": 1}` → `GET /api/ledger/verify` | `valid: false, broken_at: 1`; пропуск с этим блоком в `/passes/verify` → `valid: false` |

Другие пресеты: `storm_full` (шторм на всём море, обход по западной ветке), `congestion_astrakhan` (затор в порту Астрахань). Если допустимого маршрута нет, алерт приходит без предложения: `action: "wait"`, `to_route: null`.

`POST /api/demo/fail_next_pass` — **только демо**: следующий выпуск пропуска сорвётся.

Ошибки принятия: `409 superseded` — место на рейсе уже занято или рейс закрыт, создан новый алерт с пересчётом; `409 alert_rejected` — алерт отклонён. Повтор пропуска при новом сбое — `503 pass_issue_failed`.

### Варианты решения (`Alert.options`, `option_id`)

У алерта есть `options` — до трёх вариантов, рекомендованный первый: например `mkh` (через Махачкалу), `west` (западная ветка), `wait` (ждать следующий рейс). У каждого `id`, `title`, `route` (маршрут первого груза как пример), `delay_vs_plan_h` (к плану), `saved_hours`, `saved_rub`, `co2_delta_kg` (сумма по грузам алерта), `recommended`. Вариант `best` появляется, когда лучший обход у грузов разный.

- `POST /api/alerts/{id}/accept` `{"via": "web"}` — принимается рекомендованный, как раньше.
- `{"via": "web", "option_id": "west"}` — выбранный вариант для всех грузов алерта: резерв места, пропуска, реестр, Decision с экономией этого варианта. После принятия `items`, `totals` и `recommended` у алерта показывают принятый вариант.
- `wait` равен «Отклонить»: шлите `POST /alerts/{id}/reject`; `accept` с `option_id: "wait"` → `422 use_reject`. Неизвестный `option_id` → `404 option_not_found`.

**Когда начнётся угроза:** `Scenario.starts_in_h` и `Alert.starts_in_h` — через сколько часов от `sim_now` (storm_north и storm_full — 36, congestion_astrakhan — 18). Клиенты и бот берут число отсюда, а не считают от `created_at` (это реальное время события, а не время сценария).

**CO₂ в счётчике:** `GET /api/stats` → `co2_saved_pct` — на сколько процентов ниже CO₂ по принятым решениям к исходным маршрутам этих грузов (после storm_north — `6.9`, показывать «−6,9% CO₂»). Сумма по Decision, клиенты сами не пересчитывают.

Сравнение для карточки варианта — две строки: «Прибытие +6 ч к плану» (`delay_vs_plan_h`) и «на 42 ч быстрее ожидания следующего рейса» (`delay_vs_plan_h` варианта `wait` минус этого варианта).

## Общий сервер

Один ноутбук держит сервер, остальные ходят к нему по публичному https-адресу через SSH-туннель [pinggy](https://pinggy.io) (без регистрации и без установки: `ssh` есть в Windows).

1. **Ключи.** Перед тем как открывать адрес наружу, поставьте в `backend/.env` свои случайные `API_KEY` и `JWT_SECRET`. `caspian-dev-key` записан в этом README и годится только для локального запуска: с ним любой может вызвать `/api/demo/reset` или `/api/ledger/tamper`. Новый ключ раздайте в чате, в репозиторий не кладите. После смены `JWT_SECRET` старые токены входа перестают действовать — войдите заново.
2. **Сервер** на свежем коде: `.\run.ps1` или `.venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`. Старый процесс сначала остановить.
3. **Туннель** во втором окне:

```powershell
ssh -p 443 -o StrictHostKeyChecking=accept-new -o ServerAliveInterval=30 -R0:127.0.0.1:8000 a.pinggy.io
```

Именно `127.0.0.1`, не `localhost`: ssh в Windows разрешает `localhost` в IPv6 `::1`, а uvicorn слушает IPv4. Тогда все запросы в окне pinggy висят с пометкой `Reset`, а снаружи приходит «socket hang up».

4. В окне появятся два адреса вида `https://<слово>-<ip>.free.pinggy.net`. Раздайте первый:
   - API — `https://<адрес>/api` с заголовком `X-API-Key: <ключ>`;
   - WebSocket — `wss://<адрес>/ws?api_key=<ключ>` (через pinggy работает: проверено, события `alert.created`, `shipment.updated`, `stats.updated` приходят);
   - Swagger — `https://<адрес>/docs`.

**Ограничения бесплатного pinggy.** Туннель живёт **60 минут**, потом закрывается. **Адрес меняется при каждом перезапуске туннеля** (и после обрыва сети или сна ноутбука). Перезапустили — новый адрес в общий чат. Для защиты держите запасной вариант: локальная сеть, `http://<ip-ноутбука>:8000/api`.

**Что не сработало на ноутбуке тимлида** (сеть с VPN):
- Cloudflare quick tunnel (`cloudflared tunnel --url http://localhost:8000`): DNS не отдаёт `argotunnel.com`, а с явными узлами `--edge 198.41.192.167:7844` обрывается TLS с Cloudflare. Адрес выдаётся, но снаружи `530` / Error 1033. В другой сети может заработать.
- localhost.run (`ssh -R 80:localhost:8000 nokey@localhost.run`): соединение на порту 22 закрывается сразу.

## Регистрация и вход

Только чтобы клиент знал имя и роль пользователя. **Доступ к API не меняется:** все `/api/*`, включая `/api/auth/*`, по-прежнему требуют `X-API-Key`, а остальные эндпоинты Bearer-токен не требуют и по ролям ничего не ограничивают.

| Метод | Путь | Запрос | Ответ |
|---|---|---|---|
| POST | `/api/auth/register` | `{name, email, password, role: "logist" \| "expeditor"}` | `{token, user: {id, name, email, role}}` |
| POST | `/api/auth/login` | `{email, password}` | `{token, user}` |
| GET | `/api/auth/me` | заголовок `Authorization: Bearer <token>` | `{id, name, email, role}` |

Ошибки в общем формате: `409 email_taken` (email уже есть, регистр не важен), `401 invalid_credentials` (неверный email или пароль), `422 weak_password` (пароль короче 6 символов), `422 invalid_email`, `422 validation_error` (например, роль не из списка), `401 invalid_token` на `/auth/me` (нет токена, чужой, истёк).

- **Демо-аккаунты** создаются при первом старте, если их нет: `logist@demo.ru` и `expeditor@demo.ru`, пароль `demo123`. Для быстрого входа на защите.
- **Хранение:** `data/accounts.json` (не в git), отдельно от состояния демо: переживает `POST /api/demo/reset` и перезапуск сервера. Пароль хранится только как хэш scrypt с солью.
- **Токен:** JWT HS256 на 7 дней, подписан ключом, выведенным из `JWT_SECRET` (отдельно от ключа QR-пропусков). Клиент хранит его и шлёт только на `/auth/me`. Подтверждения почты, восстановления и смены пароля нет.

```bash
curl -X POST -H "X-API-Key: <ключ>" -H "Content-Type: application/json" -d '{"email":"logist@demo.ru","password":"demo123"}' http://localhost:8000/api/auth/login
```
```bash
curl -H "X-API-Key: <ключ>" -H "Authorization: Bearer <token>" http://localhost:8000/api/auth/me
```

## Telegram-бот

Живёт в этом же процессе (`app/bot/`, aiogram 3): polling запускается в lifespan FastAPI и вызывает движок напрямую. Если `BOT_TOKEN` в `.env` пуст, сервер стартует без бота и пишет об этом в лог.

- `/start` — приветствие, привязка пользователя, кнопки «📦 Мои грузы» и «🌊 Погода на Каспии». Для демо каждому привязанному видны все пять грузов. Привязки хранятся в `data/users.json` (не в git) и переживают и `demo/reset`, и перезапуск сервера.
- Новый алерт бот присылает сам каждому привязанному: тот же шаблон движка, что `Alert.text` на сайте, но с разметкой (заголовок отдельно, блоки, жирным риск, +48 ч, +6 ч и расчётная экономия; `Alert.text` — без разметки) и кнопки «Принять», «Другие варианты», «Отклонить».
- «Принять» — тот же `accept`, `via=telegram`. После принятия с любой платформы бот один раз редактирует сообщение (кнопки убраны, «Принято в 14:32 с сайта / из Telegram») и присылает короткий итог: строка на грузы с одинаковым маршрутом, строка про пропуска, про реестр и про расчётную экономию (без id пропусков и хэшей). Повторное нажатие — короткий ответ. При `superseded` старое сообщение теряет кнопки, приходит новый алерт. Кнопки из прошлого прогона демо (до reset) не срабатывают.
- **Лог бота (INFO, логгер `caspian.bot`):** «Бот: алерт alert-001 отправлен, получателей 2 из 2», «Бот: алерт alert-001 — сообщения отредактированы (accepted), получателей 2 из 2», «Бот: итог принятия alert-001 отправлен, получателей 2 из 2». Только тип события, `alert_id` и число получателей — без текста сообщений и chat_id. Ошибки отправки — `ERROR` с трассировкой.
- «Мои грузы» — статусы ⚪ 🔵 🔴 🟢 ✅; `reissue_pending` — отдельной строкой с кнопкой «Повторить».
- Свободный текст: если задан `LLM_API_KEY`, вопрос уходит в ИИ с инструментами только на чтение (`get_shipments`, `get_shipment`, `get_alternatives`, `get_weather`, `explain_risk`); без ключа — подсказка про кнопки.

Пример (PowerShell — `curl.exe`, не `curl`):

```bash
curl -X POST -H "X-API-Key: <ключ>" -H "Content-Type: application/json" -d '{"preset":"storm_north"}' http://localhost:8000/api/scenarios
```

### Файлы моков

`data/mock/` строит `scripts/gen_mocks.py` **этим же движком**, поэтому файлы совпадают с ответами сервера. `<имя>.json` — исходная фаза, `<имя>.storm.json` — после шторма, `<имя>.accepted.json` — после принятия. `accept.json` — полный ответ на «Принять». ID грузов `sh-01` … `sh-05`. В моках порядок фиксирован: инвойс №05 → шторм → принятие.

`delta` в `/alternatives` — к плановому маршруту: `hours` — задержка прибытия к плану по прогнозу, `rub` — доплата за перевозку, `co2_kg` — разница CO₂.

**Моки и сид руками не правим.** Поменяли расстояние, тариф или рейс в `scripts/gen_mocks.py` — запустили:

```bash
.venv/Scripts/python scripts/gen_mocks.py
```

Скрипт печатает сверку с числами сценария (298 320 ₽, 596 640 ₽, 126 груз-ч, −6,7% для №01, −6,9% для трёх грузов…) — независимым расчётом и движком — и падает, если что-то разошлось. Каждый мок проверяется Pydantic-моделями контракта.
