# Бэкенд «Каспийского диспетчера»

FastAPI, один процесс. Контракт — раздел 5 `CLAUDE.md`. Эндпоинты считает **настоящий движок сценария**: состояние в памяти из `data/seed.json`, граф networkx, расписание рейсов, формульный предиктор, диспетчер с принятием под блокировкой. Формы ответов те же, что были на моках.

## Запуск одной командой

Нужен Python 3.11+.

```powershell
.\run.ps1          # Windows
```
```bash
./run.sh           # macOS / Linux / Git Bash
```

Скрипт сам создаст `.venv`, поставит зависимости, скопирует `.env.example` → `.env` и поднимет сервер на `0.0.0.0:8000` с автоперезагрузкой.

Проверка: `curl -H "X-API-Key: caspian-dev-key" http://localhost:8000/api/stats`

Тесты: `.venv/Scripts/python -m pip install -r requirements-dev.txt`, затем `.venv/Scripts/python -m pytest` (из `backend/`).

## Для фронтенда и Flutter

- **Базовый адрес:** `http://<ip-ноутбука>:8000/api` (локально `http://localhost:8000/api`). Телефон должен быть в той же сети; IP — `ipconfig` / `ifconfig`. Эмулятор Android ходит на `http://10.0.2.2:8000/api`.
- **Ключ:** заголовок `X-API-Key: <API_KEY из backend/.env>` на **каждом** запросе к `/api/*`. По умолчанию `caspian-dev-key`. Без ключа — `401 {"error": {"code": "unauthorized", ...}}`.
- **WebSocket:** `ws://<host>:8000/ws?api_key=<ключ>` (браузер не умеет слать заголовки в WS). Сообщения `{type, payload}`: `shipment.updated`, `alert.created`, `alert.updated`, `ledger.appended`, `stats.updated`, `weather.updated`. Не успеваете с WS — опрашивайте `/shipments`, `/alerts`, `/stats` раз в 3 с.
- **Документация и «попробовать»:** http://localhost:8000/docs (Swagger, кнопка **Authorize** → ключ), схема — `/openapi.json`.
- **Время** в JSON — UTC (`2026-11-12T11:00:00Z`). Показывать в `Europe/Moscow`.
- **Ошибки** всегда `{"error": {"code": "...", "message": "..."}}`.

### Два времени

- **«Сейчас» сценария** (`sim_now`) — по нему считаются прогноз, рейсы, задержки, положение грузов. При каждом reset (и при старте) это текущее время, отброшенное до часа (10:52 → 10:00). Сценарий привязан к нему, а не к календарю: `seed.json` хранит времена от якоря `meta.now` (12 ноя 14:00 МСК), и при reset всё сдвигается на `sim_now − якорь`. Поэтому шторм всегда через 36 ч, паром А — через 44 ч, паром М — через 64 ч, и все числа сценария прежние. До следующего reset `sim_now` не идёт, числа не плывут.
- **Метки событий** (`accepted_at`, `ts` блока, время выдачи пропуска) — настоящее время: в боте «Принято в 10:52».
- `DEMO_NOW` в `.env` (UTC) фиксирует `sim_now` руками; тогда метки событий = `DEMO_NOW` + прошедшее с reset. Тесты и моки всегда идут по 12 ноя 14:00 МСК.

Повторный прогон после reset даёт те же числа и маршруты; даты, хэши блоков и токены пропусков меняются вместе со временем.

### Погода

`WEATHER_MODE` в `.env`:
- `live` (по умолчанию) — волна из Open-Meteo Marine, ветер из Open-Meteo Forecast, точки портов Каспия (Астрахань и Оля — ближайшее открытое море: сами порты на суше), `forecast_days=7`, обновление раз в 30 мин, кэш в `data/weather_cache.json`. Источник недоступен — работаем по кэшу: `source: "cache"`, `stale: true`, если кэшу больше часа. Нет ни сети, ни кэша — синтетический прогноз, `stale: true`.
- `synthetic` — всегда синтетический прогноз, сеть не трогаем, `source: "cache"`. Страховка на защиту: на Каспии правда шторм или нет интернета.

Сценарий накладывается поверх прогноза: в окне шторма волна поднимается до значений сценария, вне окна остаётся реальной. До сценария риски грузов (7/4/3% на синтетике) зависят от настоящей волны и могут немного отличаться.

### Проверка перед показом

`GET /api/demo/check` (только демо) прогоняет `storm_north` на копии исходного состояния (как после reset, с текущей погодой) и ничего не меняет. Ответ: `ok`, список сверок с эталоном (82/74/68%, +18 ч, +48 ч, +6 ч, 126 груз-ч, 596 640 ₽, рекомендован вариант через Махачкалу) и `problems` — почему разошлось, например «волна в Махачкале 2,8 м в момент отправления парома М (15 ноя, 06:00), предел 2,5 м — вариант через Махачкалу отпал». Если разошлось — `WEATHER_MODE=synthetic` и перезапуск. Та же проверка пишется в лог при старте и при каждом reset.

### Сценарий демо

| Шаг | Запрос | Что поменяется |
|---|---|---|
| Проверка | `GET /api/demo/check` | ничего; `ok: true` — числа сценария сойдутся |
| Исходное состояние | `POST /api/demo/reset` | №01–03 «В пути», риск 7/4/3%, алертов нет, счётчики 0 |
| Съёмка инвойса №05 | `POST /api/documents` (multipart `shipment_id=sh-05`, `file`) → `POST /api/documents/doc-05/confirm` `{"fields": {...}}` | черновик с полями (фарси → русский; сейчас закэшированный результат), затем пропуск `pass-05` и блок `issued` |
| Шторм | `POST /api/scenarios` `{"preset": "storm_north"}` | №01–03 «Под риском» 82/74/68%, отправление +18 ч, морской этап `blocked`, ETA +48 ч, алерт `alert-001` (`new`) |
| Сбой пропуска (по желанию) | `POST /api/demo/fail_next_pass` перед «Принять» | у первого груза `pass_state: reissue_pending`, старый пропуск активен |
| Принятие | `POST /api/alerts/alert-001/accept` `{"via": "web"}` (или `"telegram"`; `option_id` — другой вариант) | через Махачкалу, «Перестроен», новые пропуска `pass-0N-r1`, старые `reissued`, блоки `reissued`, место на пароме М зарезервировано, счётчики 126 груз-ч / 596 640 ₽ / 1 824 кг CO₂. Повтор → `already_accepted: true` |
| Повтор пропуска | `POST /api/shipments/sh-01/pass/retry` | пропуск выпущен один раз, экономия не меняется |
| Отклонение | `POST /api/alerts/alert-001/reject` | алерт `rejected` |
| Подделка реестра | `POST /api/ledger/tamper` `{"index": 1}` → `GET /api/ledger/verify` | `valid: false, broken_at: 1`; пропуск с этим блоком в `/passes/verify` → `valid: false` |

Другие пресеты: `storm_full` (шторм на всём море, обход по западной ветке), `congestion_astrakhan` (затор в порту Астрахань). Если допустимого маршрута нет, алерт приходит без предложения: `action: "wait"`, `to_route: null`.

`POST /api/demo/fail_next_pass` — **только демо**: следующий выпуск пропуска сорвётся.

Ошибки принятия: `409 superseded` — место на рейсе уже занято или рейс закрыт, создан новый алерт с пересчётом; `409 alert_rejected` — алерт отклонён. Повтор пропуска при новом сбое — `503 pass_issue_failed`.

### Варианты решения (`Alert.options`, `option_id`)

У алерта есть `options` — до трёх вариантов, рекомендованный первый: например `mkh` (через Махачкалу), `west` (западная ветка), `wait` (ждать следующий рейс). У каждого `id`, `title`, `route` (маршрут первого груза как пример), `delay_vs_plan_h` (к плану), `saved_hours`, `saved_rub`, `co2_delta_kg` (сумма по грузам алерта), `recommended`. Вариант `best` появляется, когда лучший обход у грузов разный.

- `POST /api/alerts/{id}/accept` `{"via": "web"}` — принимается рекомендованный, как раньше.
- `{"via": "web", "option_id": "west"}` — выбранный вариант для всех грузов алерта: резерв места, пропуска, реестр, Decision с экономией этого варианта. После принятия `items`, `totals` и `recommended` у алерта показывают принятый вариант.
- `wait` равен «Отклонить»: шлите `POST /alerts/{id}/reject`; `accept` с `option_id: "wait"` → `422 use_reject`. Неизвестный `option_id` → `404 option_not_found`.

Сравнение для карточки варианта — две строки: «Прибытие +6 ч к плану» (`delay_vs_plan_h`) и «на 42 ч быстрее ожидания следующего рейса» (`delay_vs_plan_h` варианта `wait` минус этого варианта).

## Telegram-бот

Живёт в этом же процессе (`app/bot/`, aiogram 3): polling запускается в lifespan FastAPI и вызывает движок напрямую. Если `BOT_TOKEN` в `.env` пуст, сервер стартует без бота и пишет об этом в лог.

- `/start` — приветствие, привязка пользователя, кнопки «📦 Мои грузы» и «🌊 Погода на Каспии». Для демо каждому привязанному видны все пять грузов. Привязки хранятся в `data/users.json` (не в git) и переживают и `demo/reset`, и перезапуск сервера.
- Новый алерт бот присылает сам каждому привязанному: тот же шаблон движка, что `Alert.text` на сайте, но с разметкой (заголовок отдельно, блоки, жирным риск, +48 ч, +6 ч и расчётная экономия; `Alert.text` — без разметки) и кнопки «Принять», «Другие варианты», «Отклонить».
- «Принять» — тот же `accept`, `via=telegram`. После принятия с любой платформы бот один раз редактирует сообщение (кнопки убраны, «Принято в 14:32 с сайта / из Telegram») и присылает короткий итог: строка на грузы с одинаковым маршрутом, строка про пропуска, про реестр и про расчётную экономию (без id пропусков и хэшей). Повторное нажатие — короткий ответ. При `superseded` старое сообщение теряет кнопки, приходит новый алерт. Кнопки из прошлого прогона демо (до reset) не срабатывают.
- «Мои грузы» — статусы ⚪ 🔵 🔴 🟢 ✅; `reissue_pending` — отдельной строкой с кнопкой «Повторить».
- Свободный текст: если задан `LLM_API_KEY`, вопрос уходит в ИИ с инструментами только на чтение (`get_shipments`, `get_shipment`, `get_alternatives`, `get_weather`, `explain_risk`); без ключа — подсказка про кнопки.

Пример (PowerShell — `curl.exe`, не `curl`):

```bash
curl -X POST -H "X-API-Key: caspian-dev-key" -H "Content-Type: application/json" -d '{"preset":"storm_north"}' http://localhost:8000/api/scenarios
```

### Файлы моков

`data/mock/` строит `scripts/gen_mocks.py` **этим же движком**, поэтому файлы совпадают с ответами сервера. `<имя>.json` — исходная фаза, `<имя>.storm.json` — после шторма, `<имя>.accepted.json` — после принятия. `accept.json` — полный ответ на «Принять». ID грузов `sh-01` … `sh-05`. В моках порядок фиксирован: инвойс №05 → шторм → принятие.

`delta` в `/alternatives` — к плановому маршруту: `hours` — задержка прибытия к плану по прогнозу, `rub` — доплата за перевозку, `co2_kg` — разница CO₂.

## Как устроено

```
app/main.py        роуты, X-API-Key, CORS, ошибки, /ws, lifespan с ботом
app/events.py      шина событий: state.events → WebSocket и Telegram-бот
app/bot/           Telegram-бот: texts (шаблоны), service (нажатия), notifier (рассылка и правки), llm
app/models.py      Pydantic-модели (раздел 4) + запросы/ответы (раздел 5)
app/state.py       состояние в памяти из seed.json, reset, пропуска, реестр, документы, asyncio.Lock
app/dispatcher.py  конвейер: affected → predict → «ничего не делать» → альтернативы → алерт → accept
app/graph.py       граф networkx, пути без заблокированных рёбер, часы/₽/CO₂ по рёбрам
app/schedule.py    время этапов, выбор первого подходящего рейса (окончание приёма, место, волна)
app/predictor.py   интерфейс предиктора + FormulaPredictor (логистическая формула); CatBoost — позже
app/scenarios.py   пресеты storm_north, storm_full, congestion_astrakhan
app/weather.py     Open-Meteo Marine (кэш, WEATHER_MODE) или синтетика, 7 суток почасово + наложение сценария
app/democheck.py   GET /api/demo/check и лог при старте/reset: storm_north на копии, сверка с эталоном
app/clock.py       sim_now (текущий час или DEMO_NOW) и event_ts
app/ledger.py      hash-chain: хэш, добавление, проверка
app/documents.py   хэш документа; распознавание vision-LLM — позже
data/seed.json     узлы, рёбра, рейсы, грузы, документы, пропуска, реестр, параметры (meta)
scripts/gen_mocks.py  строит seed.json, сверяет движок с числами DEMO_SCENARIO, пишет моки
tests/             pytest: числа сценария, одновременный accept, сбой пропуска, reset, бот с подменённым Bot API
```

**Моки и сид руками не правим.** Поменяли расстояние, тариф или рейс в `scripts/gen_mocks.py` — запустили:

```bash
.venv/Scripts/python scripts/gen_mocks.py
```

Скрипт печатает сверку с числами сценария (298 320 ₽, 596 640 ₽, 126 груз-ч, −6,7% для №01, −6,9% для трёх грузов…) — независимым расчётом и движком — и падает, если что-то разошлось. Каждый мок проверяется Pydantic-моделями контракта.
